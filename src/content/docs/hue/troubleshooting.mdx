Most Hue issues fall into one of five buckets. This page is organised stage-by-stage so you can jump to where you are stuck.

## Bridge isn't discovered

**Symptom**: Discover step returns `HUE_DISCOVERY_EMPTY` or the bridge never appears in the list.

Common causes:

1. **VLAN / guest network isolation** — bridge and LumaSync are on different subnets. Fix: put them on the same LAN, or use the **Manual IP** path.
2. **mDNS blocked** on corporate / hotel Wi-Fi. Same fix: manual IP.
3. **Bridge powered off or offline** — check the LED indicators on the bridge itself. All three should be solid.
4. **Firewall rules** blocking outbound HTTPS to `discovery.meethue.com`. LumaSync falls back to LAN mDNS automatically; still works but only if mDNS isn't blocked.

## Pairing keeps failing

**Symptom**: Status cycles through `HUE_PAIRING_PENDING_LINK_BUTTON` but never reaches `HUE_PAIRING_OK`, or you get one of the coded errors below.

From v1.4, LumaSync surfaces a specific error code for each failure mode (see [pairing errors](/docs/hue/pairing#error-codes-v14)). The mapping from code to root cause:

- **`LINK_BUTTON_NOT_PRESSED`** — you missed the ~30-second window. Click **Try again** and walk to the bridge faster.
- **`DEVICETYPE_INVALID`** — bridge refused the client identity string. Rare; reboot the bridge and retry. If it persists, file an issue with the bridge firmware version.
- **`BRIDGE_BUSY`** — another app is mid-pairing. Close the Hue app's pairing screen (or any Hue Sync Box / third-party client stuck in pairing) and retry. Only one concurrent pairing per bridge.
- **`RATE_LIMITED`** — too many pairing attempts in a short window. Wait ~60 seconds, then retry. Bridges back off aggressive clients.
- **Pairing over VPN** — bridges reject pairing from non-LAN origins as a security measure. Disconnect the VPN, pair on the local network, then reconnect VPN afterwards. Runtime streaming works over the VPN once paired; only the pairing handshake is origin-checked.

## Hue Bridge Pro: "Auth error / Credentials expired" (fixed in v1.5.4)

**Symptom (pre-v1.5.4)**: a **Hue Bridge Pro** is discovered without trouble, you press its link button, and pairing fails immediately with **Auth error — your credentials have expired**. Re-pairing gives the same result every time.

Two separate bugs stacked here. The Bridge Pro serves its local API over **HTTPS only** — port 80 is closed — while LumaSync's pairing, IP-verification, and credential-validation calls were still on plain HTTP, so they never reached the bridge. That transport failure was then mapped onto the credentials-expired message, which pointed at a problem you did not have.

v1.5.4 fixes both: the CLIP v1 calls try HTTPS first and fall back to HTTP for older firmware, and a rejected link button now shows the awaiting-link-button state. Square gen 2 bridges are unaffected — they already answered on both ports. If you are on a Bridge Pro, update from the [Download page](/download/), then pair from step 1. See [Bridge Pro pairing](/docs/hue/pairing#bridge-pro-pairing-v154) for the detail.

## `HUE_AREA_LIST_EMPTY`

**Symptom**: Pairing succeeds but the Entertainment Area dropdown is empty.

Cause: no area has been created in the Hue app yet. Follow [Entertainment Area creation](/docs/hue/entertainment-area#how-to-create-one) and click **Refresh list**.

## Stream doesn't start / status stuck on "Starting"

**Symptom**: Selected an area, turned on Ambilight mode, Hue status stays `Starting` or falls into `Failed`.

- **UDP 2100 blocked**. Hue Entertainment uses DTLS over UDP 2100 from client to bridge. Some routers / firewalls block outbound UDP. Fix: open UDP 2100 outbound on the machine running LumaSync.
- **Entertainment Area conflict**. Another app is already streaming to the same area. The bridge only allows one streamer per area at a time. Fix: close the other app (Hue Sync Box apps are the usual culprit).
- **Credentials rotated**. The bridge occasionally cycles credentials after firmware updates. LumaSync surfaces a **Repair Hue credentials** banner; click it and re-run steps 2–4 of pairing.

## `HUE_STREAM_NOT_READY_ACTIVE_STREAMER` (retired in v1.5.2)

**Symptom (pre-v1.5.2)**: Stop streaming, immediately try to start again, the bridge replies 403 with "active streamer". Required ~10 s of waiting before the bridge cleared its session slot.

From v1.5.2, LumaSync emits an explicit DTLS `close_notify` alert before dropping the socket and dedupes foreground / background deactivate calls through a single-shot atomic token. The bridge clears its "active streamer" slot immediately on stop, so back-to-back stop / start is now reliable on the same session. The 1 s defensive sleep that was the previous workaround has been removed.

If you still see this on v1.5.2+, another client is genuinely holding the slot — typically the Hue app's own play screen, a Hue Sync Box app, or a third-party Entertainment client. Stop streaming there first.

From v1.5.3 the active-streamer banner clears itself. While the area is held by another streamer, LumaSync re-probes readiness every 3 seconds (instead of the 15-second healthy cadence) and dismisses the banner within ~3 seconds of the other session releasing the slot — no manual revalidate needed.

## Status stuck on "Reconnecting" (fixed in v1.5.3)

**Symptom (pre-v1.5.3)**: the Hue stream stalls permanently on `Reconnecting` and never recovers.

Earlier builds could deadlock here when a status poll raced the reconnect monitor for the same shutdown signal. v1.5.3 keys the monitor's guard off an explicit in-progress flag, so the restart always proceeds and the stream self-heals. If you are on v1.5.2 or earlier and hit a permanent `Reconnecting` status, restart the stream manually or update to v1.5.3.

## Bulbs respond but look "laggy"

**Symptom**: Lights update but feel delayed compared to the screen.

- **Network hop count high**. Check Wi-Fi signal between the machine and the bridge. Hop-to-hop latency shows up as visual lag. Pulling the bridge closer — or wiring it to Ethernet — tightens response.
- **Zigbee mesh is stressed**. Bulbs far from the bridge relay through neighbours. Add a bulb in between, or move the bridge. Hue's app can show you the mesh diagnostics (Settings → Bridge → Advanced).
- **Expecting gaming latency**. The 20 Hz bridge cap is the real ceiling. If 50 ms visual lag is unacceptable for your use case, USB LED strips are a better primary target with Hue as secondary room fill.

## Some bulbs in the area don't respond

**Symptom**: Entertainment Area has 5 bulbs but only 3 are reacting.

- **Unreachable bulb**. Open the Hue app → tap the bulb in the room view — if it shows "Unreachable", fix power or re-pair the bulb with the bridge first. LumaSync can't stream to a bulb the bridge itself can't see.
- **Bulb doesn't support Entertainment**. Warm-white-only bulbs respond only to brightness, not colour, and may appear "stuck" at whatever colour the area last saw before they joined. Remove them from the area via the Hue app if that isn't what you want.

## Stop didn't fully complete (`HUE_STOP_TIMEOUT_PARTIAL`)

If stopping the Hue stream times out partway, LumaSync raises a `HUE_STOP_TIMEOUT_PARTIAL` fault. From v1.5.3 this fault surfaces a **Retry Stop** action hint — matching the inline recovery CTA in the device panel — so you can re-issue the stop with one click. The bridge also times out the entertainment session server-side, so the slot clears regardless.

## When to just repair

Not every failure is worth diagnosing. If all else fails and you have five minutes:

1. Hue app → Settings → Entertainment areas → delete the broken area.
2. LumaSync → Settings → Hue → **Forget bridge**.
3. Recreate the area in the Hue app with your current bulb lineup.
4. Walk back through pairing from step 1.

Almost always faster than debugging.
