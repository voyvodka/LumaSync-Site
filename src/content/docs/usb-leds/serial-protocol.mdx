LumaSync's USB pipeline uses a **LumaSync-specific serial frame** over a 115200-baud link. This page is the wire-level reference — useful if you're flashing firmware onto a microcontroller, writing your own controller, or debugging why a kit isn't lighting up.

## LumaSync v1 frame, with an Adalight fallback

LumaSync's default USB framing is **not** Adalight-compatible: different magic bytes, different length encoding, different checksum. A controller running unmodified [Adalight firmware](https://learn.adafruit.com/adalight-diy-ambient-tv-lighting) will **not** respond to an unconfigured LumaSync install.

From **v1.4**, the **Lights** page has a **Firmware Profile** choice (LumaSync v1 · Adalight). Switch to **Adalight** and LumaSync emits the legacy `Ada` header framing byte-for-byte; the choice is saved, so it survives a restart. Keep the default **LumaSync v1** profile for firmware that reads the frame below.

## Wire format (v1)

Each frame is:

```
Header:   0xAA 0x55                (2 bytes, magic)
          BRIGHTNESS                (1 byte, 0–255)
          LED_COUNT_LO              (1 byte, low byte of LED count)
          LED_COUNT_HI              (1 byte, high byte of LED count — little-endian u16)
Payload:  pixel data                (LED_COUNT × 3 bytes, R G B)
Trailer:  XOR_CHECKSUM              (1 byte, XOR of every preceding byte)
```

For a 120-LED strip: 5 bytes header + 360 bytes RGB + 1 byte checksum = 366 bytes per frame. At 115200 baud with 8-N-1 framing the link carries 11,520 bytes a second, so that frame takes about 32 ms on the wire.

### Brightness

The third byte carries LumaSync's brightness setting as `floor(brightness × 255)`: 255 at full, 204 at 80 %. The colour bytes are **not** scaled by it, so the firmware is expected to apply the brightness itself. Adalight framing has no brightness byte; with the Adalight profile selected, LumaSync locks its brightness controls and the strip runs at whatever brightness the firmware sets.

### Pixels and the LED Chip Type setting

Each LED takes three bytes, in the order `R G B`.

The **Devices** page has an **LED Chip Type** setting — **WS2812B (3-byte RGB)** or **SK6812 RGBW (4-byte)**. The choice is saved, but it does not change the stream: every frame carries 3-byte RGB pixels, whichever chip is selected. There is no wire-level tag for the chip type either, so the firmware is expected to know which physical strip it drives.

### Gamma correction

Pixel bytes are **gamma-corrected on the host** with a 2.2 power curve: each channel value `v` goes out as `round((v / 255)^2.2 × 255)`, so a mid-grey 128 is sent as 56. Firmware should not apply additional gamma. If your LEDs look crushed at low values or blown out at high values, double-check the firmware isn't re-gamma-ing on top.

On the LumaSync v1 path the curve is fixed: the **Gamma Red**, **Gamma Green** and **Gamma Blue** sliders in the colour-correction panel only change it under the Adalight profile. White-point (Kelvin) and saturation apply on both.

### Byte order

LED count is **little-endian u16** (LSB first). Adalight uses big-endian and encodes `count − 1`; LumaSync v1 uses straight LE and the actual count. This is the single detail most likely to trip up anyone porting from an Adalight sketch.

## Baud rate

**115200**, hard-coded in LumaSync: the port is always opened at that rate, so the firmware has to use it too. Its 11,520 bytes a second are what limit the frame rate (see [Frame rate](#frame-rate)).

## The handshake

**Run Health Check** on a connected USB controller in **Devices** walks through four steps:

1. **Port visibility** — the selected port is in the system's serial-port list.
2. **Port support** — it is a USB serial adapter on LumaSync's supported list (see [USB controllers](/docs/usb-leds/controllers/)).
3. **Connect and verify** — LumaSync opens the port at 115200 baud, then waits 2 seconds for the controller to finish its reset (Arduino-class boards auto-reset on serial open).
4. **Firmware handshake** — LumaSync sends a 5-byte PING, `AA 55 10 00 EF` (magic, opcode `0x10`, payload length 0, XOR), and waits up to 2 seconds for a 7-byte PONG: `AA 55 11`, the firmware version as a little-endian u16 (`0x0104` is 1.4), a profile byte (`0x01` LumaSync v1, `0x02` Adalight) and an XOR of the six bytes before it.

The handshake step reports one of three codes:

| Code | Meaning |
| --- | --- |
| `SERIAL_HEALTH_OK` | A valid PONG came back; the firmware version, profile and round-trip time are shown |
| `SERIAL_HEALTH_HANDSHAKE_TIMEOUT` | No complete reply within 2 seconds |
| `SERIAL_HEALTH_PROTOCOL_ERROR` | A reply came back, but its magic, opcode, checksum or profile byte was wrong |

Adalight firmware has no PING/PONG, so with the Adalight profile a failed handshake is expected. A failed handshake is not fatal anyway: LumaSync streams frames whenever the port is connected and assumes the firmware cooperates. If the strip lights up, you're fine.

## Frame rate

LumaSync paces USB frames from your LED count so that each frame fits the 115200-baud budget, between 10 and 60 frames per second:

- **60 LEDs** → ~60 FPS
- **120 LEDs** → ~30 FPS
- **200 LEDs** → ~19 FPS

No configuration is needed. When capture and sending take longer than that interval, LumaSync slows down instead of queueing frames. While Ambilight runs, the **Capture → Strip** readout on the **Lights** page shows the actual rate.

## USB output: per-LED sampling

From **v1.4**, each LED samples its own edge region of the screen, anchored to the LED layout you set in **LED Setup** (edge counts, start anchor, direction, bottom gap). The strip's colour is no longer a single RGB triplet extended across every LED — every pixel is computed from the matching screen zone.

## Firmware implementations

- **No reference firmware is published.** To work with the default profile, a sketch reads the frame above — wait for `AA 55`, read the brightness and the little-endian count, then `count × 3` colour bytes, and check the XOR — and answers the health check's PING with a PONG.
- **Porting from Adalight** — the core loop is similar; what changes is the magic bytes (`Ada` → `0xAA 0x55`), the brightness byte that follows them, the length encoding (BE `n−1` → LE `n`), the checksum (Adalight's `hi ^ lo ^ 0x55` over the length → one XOR over the whole frame, at the end), and answering the PING.
- **Adalight profile (v1.4+, opt-in)** — if you already have Adalight firmware flashed (common on "ambilight USB kit" marketplace purchases), choose the Adalight profile on the **Lights** page instead of reflashing. LumaSync emits Adalight framing byte-for-byte, colour corrections included, with no brightness byte.

## Why not raw APA102 / SPI?

USB-serial buys hot-pluggable hardware at the cost of a latency ceiling. SPI-attached strips (APA102, SK9822) are faster and don't need a microcontroller intermediary — but they require wiring into the host machine, which excludes 99% of desktop users. USB-serial is the pragmatic path.
