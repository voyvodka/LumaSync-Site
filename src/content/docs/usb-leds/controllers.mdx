LumaSync's USB LED path drives an addressable strip through a USB-to-serial controller, streaming RGB frames at 115200 baud using the [LumaSync v1 serial frame format](/docs/usb-leds/serial-protocol/) — not Adalight. An **opt-in Adalight profile** shipped in v1.4; choose **Adalight** under **Firmware Profile** on the **Lights** page to keep existing Adalight controllers running unchanged.

## Supported chipsets

LumaSync connects only to USB serial adapters on its allowlist. From v1.5.0 the list is:

| Chip | USB VID:PID | Where you'll find it |
| --- | --- | --- |
| **CH340** | `1A86:7523` | Most cheap Arduino-clone ambilight kits; "ambilight USB kit" on the usual marketplaces. |
| **CH341** | `1A86:5523` | CH340's sibling; some module vendors label them interchangeably. |
| **FTDI FT232R** | `0403:6001` | Higher-end kits, DIY boards using genuine FTDI. |
| **FTDI FT232H** | `0403:6014` | High-speed FTDI variant; behaves identically to FT232R at 115200 baud. |
| **Prolific PL2303** | `067B:2303` | Common on legacy Arduino-clone boards. |
| **Silicon Labs CP2102** | `10C4:EA60` | Frequently shipped on ESP32 and ESP8266 dev kits. |
| **Silicon Labs CP2104** | `10C4:EA70` | Compact, low-power, frequently shipped on ESP32 dev kits when the ESP isn't routing serial directly. |
| **Arduino Uno** | `2341:0043`, `2341:0001` | Genuine Uno boards, R3 and the earlier USB ID. |

LumaSync scans the OS's serial port list and matches it against these VID:PIDs. The **Devices** page shows matches under **Supported controllers** and everything else under **Other serial ports**, but **Connect** refuses anything that is not on the list with `PORT_UNSUPPORTED` — Bluetooth virtual ports like `/dev/cu.Bluetooth-Incoming-Port` on macOS, PCI / motherboard serial, "Unknown"-classed ports, and USB adapters with any other VID:PID.

## LED Chip Type — WS2812B vs SK6812 RGBW

The **Devices** page has an **LED Chip Type** setting with two options, **WS2812B (3-byte RGB)** and **SK6812 RGBW (4-byte)**. It is one setting for the app, not one per controller, and while the choice is saved, it does not change what LumaSync sends: every frame carries three bytes per LED, `R G B`, whichever chip is selected.

- **WS2812B** (RGB, 24 bits per pixel) — the default for the vast majority of ambilight kits, and what the stream is built for.
- **SK6812 RGBW** (RGB + dedicated white, 32 bits per pixel) — LumaSync does not derive the white channel, so the firmware has to turn the RGB bytes into the strip's four channels.

## How to check what you have

### macOS

```bash
ioreg -p IOUSB -l -w 0 | grep -iE 'idVendor|idProduct|CH34|FT232|PL2303|CP210|Arduino'
```

Look for `0x1a86` (WCH / CH340 / CH341), `0x0403` (FTDI), `0x067b` (Prolific), `0x10c4` (Silicon Labs) or `0x2341` (Arduino) in the vendor field.

### Windows

**Device Manager** → **Ports (COM & LPT)** — the device name usually spells out the chipset:

- "USB-SERIAL CH340 (COM3)" → CH340
- "USB Serial Port (COM4)" → FTDI; Properties → Details → Hardware IDs shows `VID_0403&PID_6001` or `VID_0403&PID_6014`.
- "Prolific USB-to-Serial Comm Port" → PL2303
- "Silicon Labs CP210x USB to UART Bridge" → CP2104

### Linux

```bash
lsusb | grep -iE '1a86|0403|067b|10c4|2341'
```

And the serial port is typically `/dev/ttyUSB0` once the kernel driver loads (`ch341` for CH340 / CH341, `ftdi_sio` for FTDI, `pl2303` for Prolific, `cp210x` for Silicon Labs); an Arduino Uno shows up as `/dev/ttyACM0` through `cdc_acm`.

## Drivers

- **macOS 12.3+**: every adapter on the list works with bundled drivers. No third-party install needed.
- **Windows 10/11**: CH340 / CH341 drivers sometimes need a manual install from WCH's website (search "CH340 driver"). FTDI, Prolific, and Silicon Labs drivers install automatically through Windows Update.
- **Linux**: kernel ships all of these drivers (`ch341`, `ftdi_sio`, `pl2303`, `cp210x`, `cdc_acm`) since forever. If `/dev/ttyUSB0` doesn't appear, your user probably isn't in the `dialout` group: `sudo usermod -aG dialout $USER` then log out and back in.

## Firmware on the controller

The controller needs firmware that reads the **LumaSync v1 frame at 115200 baud** — see [Serial protocol](/docs/usb-leds/serial-protocol/) for the full wire spec.

- **No reference sketch is published.** The serial-protocol page has the byte-level format, so you can port an existing sketch or write your own.
- Most "ambilight USB kit" marketplace products ship pre-flashed with **Adalight firmware**. From v1.4, LumaSync includes an **opt-in Adalight encoder profile** — choose **Adalight** under **Firmware Profile** on the **Lights** page, and LumaSync emits the legacy Adalight framing instead of its native v1 frame. Alternatively, flash firmware that reads the v1 frame.
- Don't change the baud rate from 115200: LumaSync always opens the port at that rate.

## "My controller isn't on the list"

The list covers the vast majority of marketplace ambilight kits and ESP32 dev boards. If your chip is something else (e.g. a WCH CH9102), LumaSync lists it under **Other serial ports** but **Connect** refuses it with `PORT_UNSUPPORTED`, even when it is a standard USB-to-serial bridge at 115200 baud. There is no manual override.

Adding a chipset to the list requires a code change in the app — please open an [issue](https://github.com/voyvodka/LumaSync/issues) with the VID:PID if you'd like it added.
