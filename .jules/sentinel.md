## 2026-04-27 - [JSON-LD Serialization XSS]

**Vulnerability:** The JSON-LD schema objects generated in `src/lib/seo.ts` and inserted via `JSON.stringify(schema)` inside a `<script type="application/ld+json">` tag using Astro's `set:html` attribute were vulnerable to Cross-Site Scripting (XSS). If the title or description (e.g. from an Astro Markdown page's frontmatter) contained a string like `</script><script>alert(1)</script>`, `JSON.stringify` would correctly encode the characters for JSON, but the browser would see the `</script>` tag and break out of the script tag context, executing the payload. **Learning:** `JSON.stringify` does not escape HTML control characters `<` and `>`. When injecting JSON directly into a script tag using an unescaped raw HTML mechanism (like Astro's `set:html`), you must manually replace these characters to avoid breaking out of the `<script>` context. **Prevention:** Always escape `<` to `\u003c`, `>` to `\u003e`, and `&` to `\u0026` after using `JSON.stringify` when placing its output directly inside a `<script>` tag.

## 2026-05-02 - [Raw HTML Injection XSS in Markdown Parsing]

**Vulnerability:** The `changelog.astro` page read the upstream `CHANGELOG.md` file, parsed it with `marked.parse()`, and injected the resulting string directly into the page via Astro's `set:html` attribute without any sanitization. If a malicious user were able to inject an XSS payload (e.g. `<script>alert('XSS')</script>`) into the upstream `CHANGELOG.md` file, the `set:html` attribute would render it directly onto the site context when deployed, leading to arbitrary JS execution on the client-side. **Learning:** `marked.parse()` does not sanitize the generated HTML output. It blindly converts Markdown syntax to HTML while preserving inline raw HTML tags. Using an unsafe attribute like Astro's `set:html` (or React's `dangerouslySetInnerHTML`) to insert `marked.parse()` output directly exposes the application to XSS vulnerabilities. **Prevention:** Always pipe the output of Markdown parsers like `marked.parse()` through an HTML sanitizer like `DOMPurify` (or `isomorphic-dompurify` for server-side compatibility) before inserting it into the DOM via raw HTML mechanisms.

## 2026-05-05 - [Raw HTML Injection XSS in Component Data]

**Vulnerability:** The `community.astro` page rendered an array of objects `triage` into a definition list `<dl>`. It injected raw HTML from the objects into a `<dd>` element without sanitization using Astro's `set:html` attribute (`<dd set:html={item.a} />`). While the items were currently hardcoded, this pattern posed an XSS risk if the data source were ever changed to a dynamic or user-provided input. **Learning:** Hardcoded arrays or objects in component state that contain raw HTML and are injected using `set:html` create a latent XSS vulnerability. If the data source changes or is extended to include user input, the application instantly becomes vulnerable without any changes to the rendering logic. **Prevention:** Always sanitize any data passed to a raw HTML rendering mechanism (like `set:html` or `dangerouslySetInnerHTML`), regardless of whether the data is currently hardcoded or dynamic. Use a sanitizer like `DOMPurify` (or `isomorphic-dompurify` for server-side compatibility) to clean the input before rendering.

## 2026-05-05 - [DOM-based XSS in Pagefind Search Results]

**Vulnerability:** In `src/components/Search.astro`, Pagefind search results were directly injected into the DOM via `innerHTML` to display the result excerpts. While the URL, title, and other metadata were properly escaped, the `excerpt` property was injected directly (`${r.excerpt || ''}`). Since the excerpt text originates from the indexed content, an attacker could potentially introduce malicious HTML tags into the indexed text and trigger XSS when users perform a search. **Learning:** Even when using a search indexing tool, if the output is inserted using raw DOM mechanisms like `innerHTML`, all dynamically inserted text values must be properly sanitized. Pagefind includes `<mark>` and `</mark>` tags to highlight matched search terms within the `excerpt`. Stripping out or fully escaping everything would break the search highlight UI. **Prevention:** Rather than directly trusting the excerpt string or escaping everything completely, sanitize the search excerpt text by first running it through a robust HTML escaping mechanism, and then selectively restoring the specific HTML tags required for functionality (in this case, just the `<mark>` tags using `.replace()`).

## 2026-05-06 - [Missing Single Quote Escape in JSON Stringify]

**Vulnerability:** In `src/components/Schema.astro`, when injecting JSON-LD data into `<script>` tags via `set:html`, `JSON.stringify` output was being escaped for `<`, `>`, and `&`, but not for single quotes (`'`). This omission creates an XSS vulnerability vector, allowing an attacker to potentially break out of a string context within the generated JSON if the payload contained unescaped single quotes. **Learning:** `JSON.stringify` output does not escape HTML control characters or quotes by default. When injecting JSON data directly into `<script>` tags, especially those rendered with `set:html`, failure to escape single quotes can lead to script breakouts. A comprehensive sanitization strategy must include replacing `'` with `\u0027`. **Prevention:** When injecting JSON data into Astro `<script>` tags via `set:html`, `JSON.stringify` output must have HTML control characters (`<`, `>`, `&`) and single quotes (`'`) manually escaped to prevent XSS script-breakout vulnerabilities. Use `.replace(/'/g, '\\u0027')` alongside other character replacements.

## 2026-05-12 - [Incomplete HTML Escaping in Custom Utilities]

**Vulnerability:** A custom `escapeHtml` utility in `src/components/Search.astro` lacked escaping for single quotes (`'`). This could allow attackers to break out of single-quoted HTML attributes or exploit XSS if Pagefind indexed malicious content. **Learning:** Homegrown sanitization functions frequently miss edge cases. While escaping `<` and `>` prevents direct script injection, unescaped single and double quotes leave attributes vulnerable. **Prevention:** Rely on established libraries like `DOMPurify` whenever possible. If custom escaping is strictly necessary (e.g., for performance or to preserve specific tags like `<mark>`), ensure all 5 key characters (`&`, `<`, `>`, `"`, `'`) are covered.

## 2026-05-27 - [Overly Permissive Content Security Policy]

**Vulnerability:** The `Content-Security-Policy` header defined in `public/_headers` included the `https:` scheme wildcard in the `script-src` and `connect-src` directives (`script-src 'self' 'unsafe-inline' https:;`). This allowed any script hosted on an HTTPS origin to execute and any HTTPS endpoint to be connected to, completely bypassing the CSP's restriction on external scripts (like `'self'`). If an attacker were able to inject a script tag referencing an external HTTPS source (e.g., `<script src="https://attacker.com/malware.js"></script>`), it would execute successfully. **Learning:** Using scheme wildcards like `https:` in sensitive CSP directives like `script-src` and `connect-src` nullifies the protection those directives provide against cross-site scripting (XSS) and data exfiltration. It essentially allows the browser to trust the entire internet. **Prevention:** Remove scheme wildcards like `https:` from `script-src`, `connect-src`, and `object-src`. Rely on `'self'` and explicitly define only the specific external domains required by the application.

## 2026-06-15 - [Referer Leakage on External Links]

**Vulnerability:** External links (`<a>` tags) across the site, including community forums, GitHub source links, and download sources, did not include the `rel="noopener noreferrer"` attribute. When a user clicked these links, the browser could send a `Referer` header to the external domain, potentially leaking sensitive query parameters, user paths, or internal routing information. Additionally, omitting `noopener` leaves the application vulnerable to reverse tabnabbing attacks, where the newly opened tab can manipulate the original page's `window.opener` object. **Learning:** Default HTML anchor tags with `href` pointing to external domains (e.g., GitHub, Hue Developer Portal) do not provide privacy or security protections out of the box. Assuming modern browsers mitigate all tabnabbing risks is unsafe, and preventing `Referer` leakage is a necessary defense-in-depth measure. **Prevention:** Always add `rel="noopener noreferrer"` to external links across the codebase to ensure both `window.opener` separation and `Referer` header stripping, improving both security and user privacy.

## 2026-06-22 - [Referer Leakage — remaining surfaces]

**Vulnerability:** The 1.1.25 external-link hardening pass missed a few outbound links that resolve at render time rather than as static `href` literals: the 404 page's recovery links (the GitHub "Report a bug" entry), the `/community/` FAQ answers built as inline HTML strings (the `/issues` and `/discussions/categories/ideas` GitHub links), the `/community/` "forums" cards (`href={f.disabled ? undefined : f.href}`), and the `/download/` per-OS asset cards (`href={disabled ? undefined : href}`). None carried `rel="noopener noreferrer"`. **Learning:** Conditional or string-concatenated `href` values are easy to skip in a grep-driven audit because they don't match a literal `href="https...`. **Prevention:** When an anchor's `href` is conditional, mirror the guard on `rel` (`rel={cond ? undefined : 'noopener noreferrer'}`) or, for external-only link lists, derive it (`rel={href.startsWith('http') ? 'noopener noreferrer' : undefined}`).

## 2026-06-29 - [DOM XSS via javascript: URIs in Dynamic Hrefs]

**Vulnerability:** In `src/components/Search.astro`, Pagefind search results were directly injected into the DOM via `innerHTML`. The result's `url` property was passed through `escapeHtml()` before being placed in the `href` attribute of the result `<a>` tag (`href="${escapeHtml(r.url)}"`). However, standard HTML escaping (converting `<`, `>`, `&`, `"`, `'`) does not prevent `javascript:` or `data:` URIs from executing when a user clicks the link. If an attacker could influence the indexed URLs to include a payload like `javascript:alert(1)`, they could execute arbitrary JavaScript upon a link click despite the HTML escaping. **Learning:** HTML escaping is insufficient when dealing with dynamically injected URLs in `href` or `src` attributes. An attacker can use valid URI schemes (like `javascript:`) that don't rely on HTML characters to execute scripts. When using raw DOM mechanisms like `innerHTML`, dynamically inserted URLs must have their schemes validated. **Prevention:** Always validate the URL scheme when injecting dynamically generated URLs into `href` attributes. Use the native `URL` constructor with a dummy base (e.g., `new URL(url, 'http://localhost')`) to safely allow relative paths while enforcing secure `http:`/`https:` protocols, and reject or neutralize any other scheme before passing the URL to HTML escaping.

## 2026-08-16 - [sanitizeUrl returns the parsed URL, not the caller's string]

**Not a vulnerability.** An automated report (PR #128) claimed `sanitizeUrl()` in `Search.astro` could be bypassed with `java\tscript:alert(1)` or `j\navascript:alert(1)`, on the reasoning that `new URL()` would read those as a relative `http:` path while the HTML parser strips the control character and executes them. That reasoning is wrong: the WHATWG URL parser removes tab, LF and CR from the input _before_ parsing, so `new URL("java\tscript:alert(1)", base).protocol` is `"javascript:"` and the existing scheme check already returned `'#'`. Every C0 control character was swept in leading and interior position against a simulation of the browser's real `href` pipeline — strip leading/trailing ASCII whitespace, then URL-parse — looking for an input the guard sees as `http:` but the DOM executes as `javascript:`. There were none, because both parsers remove the same interior set. Reachability was weak besides: `r.url` comes from Pagefind's build-time index over this repo's own content.

**Learning:** A parser-differential claim is only real if the two parsers actually differ; check that before assigning severity. The bypass class described here does not exist for tab/LF/CR, and the characters the URL parser _does_ keep (`\x00`-`\x08`, `\x0B`, `\x0C`, …) are equally kept by the HTML parser in interior position, so they stay a relative path rather than becoming a scheme.

**Prevention (kept anyway):** `sanitizeUrl` now returns the parsed output — `parsed.pathname + parsed.search + parsed.hash` for the dummy origin, `parsed.href` otherwise — rather than the caller's string. Not because a bypass was found, but because validating one string and returning another is a shape that invites one. Do not record this entry as a fixed XSS; it was not.
